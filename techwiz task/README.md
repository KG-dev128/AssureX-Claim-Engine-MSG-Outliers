# AssureX — document-backed warranty assessment

A Flask application for uploading warranty evidence, reading it with OCR,
confirming extracted fields, and evaluating the claim with the supplied trained
model and configurable warranty rules.

## Run on this computer

```powershell
.\run.ps1
```

Open http://127.0.0.1:5000 and create an account. There are no default accounts,
seeded claims, or sample verdicts. The repaired `.runtime` environment is separate
from the original `.venv`, which points to a Python installation on another PC.

## Roles and authentication

The app issues an HS256 JWT at sign-in. The token is returned to API clients and
also stored in an HTTP-only, SameSite=Strict cookie for the browser. Protected
endpoints validate its signature and expiry, then reload the account and role
from SQLite before authorizing each request. API clients may send the same token
as `Authorization: Bearer <token>`. Tokens expire after eight hours. Set
`COOKIE_SECURE=1` behind HTTPS. Customer registration creates only the `user`
role; staff accounts require an administrator.

For a new database, provision the first admin from the project directory with
`.\.runtime\Scripts\python.exe provision_admin.py`. It prompts for the
password without echoing it and creates no sample accounts. Admins can then
provision accounts in `/admin.html`. Each role has its own dashboard.

For a clean installation with Python 3.12:

```powershell
python -m venv .runtime
.\.runtime\Scripts\python.exe -m pip install -r requirements.txt
.\run.ps1
```

EasyOCR downloads recognition weights on its first run if they are not cached.
This computer already has English recognition weights. PDF OCR additionally
requires Poppler on PATH; image uploads do not. Set `ASSUREX_OCR_ENGINE` to
`auto`, `easyocr`, `paddleocr`, or `tesseract` when starting `app.py` directly.
Tesseract requires its separately installed executable; PaddleOCR is optional.

## What produces an assessment

1. Uploaded document bytes are hashed; missing uploads have no invented hash.
2. OCR returns real text, recognized fields, and engine status. Unreadable fields
   remain empty. The user sees source text beside editable fields.
3. Confirmed facts are mapped to the **28 input columns in the saved binary**.
   Its schema differs from the accompanying notebook/old README. The deployed
   artifact is a scikit-learn 1.8.0 logistic-regression pipeline with preprocessing.
4. Its real class probabilities are returned. Missing model dependencies or
   inference errors produce `prediction: null`, `confidence: null`, and manual
   review; there is no rule-based substitute disguised as a model prediction.
5. Warranty rules, evidence gaps, duplicates, contradictions, and low confidence
   inform the final recommendation. The probability view remains distinct from
   the final recommendation. The supplied policies are **project reference
   policies**, not verified manufacturer terms.
6. A claim-specific PDF and hash-chained audit record are generated. A nonexistent
   claim cannot obtain a generic approval certificate.

An independent claim-card image classifier is trained from the SRS-labelled
synthetic corpus. It uses HOG image features and multinomial logistic regression
with an explicit `Valid Claim`, `Invalid Claim`, `Manual Review` label map. It is
identified as an in-house visual model; the old H5/`Class 1` labels are not
misrepresented as a Google Teachable Machine export. Its held-out synthetic test
accuracy is 90.22% (225 cards, with regularization selected on validation); this
does not claim real-world claim accuracy. The dataset construction, claim-level
split, and held-out metrics are documented in
[`CLAIM_CARD_DATASET.md`](CLAIM_CARD_DATASET.md) and
[`models/claim_card_model_metrics.json`](models/claim_card_model_metrics.json).

The service desk can create a claim for an existing customer and product, or
capture product details during intake. Assessment notifications go to the
customer account. Warranty expiry notices are generated by a daily background
job rather than when a notification list is opened. Admins can review and
acknowledge recorded login bursts, duplicate evidence, upload-type errors, and
model confidence/failure/disagreement events.

Unknown date features are passed as missing to the model's fitted imputer.
Warranty expiry is derived from the confirmed purchase date and warranty months
when a separate start/expiry date is not provided. The 70% review threshold is
a configurable application decision in `app.py`, not a measured accuracy claim.
The existing tabular model and its performance report have not been retrained or
independently validated for real-world claim accuracy.

## Data and interface

New accounts, claims, evidence, audit logs, and support requests live in
`instance/` (git-ignored). `ASSUREX_DATA_DIR` can point to another isolated store.
Historical `data/` and `outputs/` sample artifacts and training datasets are not
loaded into the web app. They were retained as source material, not deleted.
Customer records and PDFs require the owning account; staff endpoints require
the corresponding role. Public registration only creates `user` accounts.

The frontend uses shared styles in `Frontend/assets/css/`, including
`workbench.css`, `ui-polish.css`, `experience.css`, and role-specific styles,
with behavior in `Frontend/assets/js/workbench.js`: a consistent paper/ink interface, a
document workbench, source-text verification, model probabilities, role-aware
navigation, live role dashboards, and searchable claim ledgers.
There are no simulated progress percentages, preset verdicts, or invented
dashboard totals. Loading messages follow actual requests.

The maintained website files live in `Frontend/`. Copy that entire folder when
sharing the project on USB; `app.py` serves the `Frontend/` folder beside itself.
The old `build_interface.py` generator is retired because it would replace
several current pages with an outdated design. It now exits without changing
files. CSS and JavaScript URLs include a build version so copied updates trigger
fresh browser requests; when editing those assets, update the `v=` value in the
HTML page references as well. The included `run.ps1` starts Flask on
`127.0.0.1`, which is local to the computer running it.

## Verify

```powershell
.\.runtime\Scripts\python.exe -m pytest tests -q
```

The integration suite creates a clearly labeled test document in memory and
uses an isolated temporary database. It exercises real EasyOCR, both saved
models, PDF output, missing dependencies, missing evidence, authentication,
claim ownership, service-center intake, scheduled-alert idempotence, admin alert
acknowledgement, and label mapping. No test data is seeded into the running
application.

The development server binds to localhost. Multi-process deployments should
replace the local file registry/audit locks with transactional storage before
serving concurrent workers.

## Shared Neon database

The app uses Neon PostgreSQL when `DATABASE_URL` is present in the project
root `.env`; the `.env` file is ignored by Git because it contains credentials.
Install the dependencies in `requirements.txt` before starting the server. On
Windows, from this folder run
`.\.runtime\Scripts\python.exe -m pip install -r requirements.txt`.
Keep the same `.env` connection string in each trusted project copy to share
accounts and application records. Never commit or send the `.env` file.
